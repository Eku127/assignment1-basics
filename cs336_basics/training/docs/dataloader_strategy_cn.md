# LLM 训练中的高效数据加载策略

本文档总结了在现代大型语言模型（LLM）训练中广泛采用的一种高效、可扩展的数据加载（Data Loading）策略。

## 核心思想

该策略的核心思想可以概括为两步：
1.  **拼接 (Concatenate):** 将所有不同来源的文本数据预处理并拼接成一个单一、巨大的 Token 序列。
2.  **切片 (Slice):** 从这个巨大的序列中，通过滑动窗口的方式切分出固定长度的、用于训练的 `(输入, 目标)` 数据对。

---

## 第一步：数据预处理 - 拼接所有文本

在训练语言模型之前，我们需要先将原始文本数据转换成模型能够理解的格式。

1.  **分词 (Tokenization):** 使用一个分词器（Tokenizer）将所有的原始文本（如网页、书籍、代码等）转换成数字 Token 组成的序列。
2.  **拼接 (Concatenation):** 将所有独立的 Token 序列直接拼接成一个非常长的单一序列。这个序列的长度 `n` 可以达到数十亿甚至更多。
3.  **添加分隔符 (Add Delimiter):** 为了让模型能够区分不同文档的边界，通常会在拼接不同文档的 Token 序列之间插入一个特殊的分隔符 Token，例如 GPT 系列使用的 `<|endoftext|>`。

### 示例

-   文档1 "Hello world" 被分词为 `[123, 456]`
-   文档2 "Bye bye" 被分词为 `[789, 789]`
-   分隔符 `<|endoftext|>` 对应的 Token ID 是 `[50256]`

拼接后的最终长序列为：`[123, 456, 50256, 789, 789, ...]`

---

## 第二步：创建训练批次 (Batching)

有了这个超长的 Token 序列后，`DataLoader` 的任务就是从中创建出一批批（Batches）用于模型训练的数据。

-   `m`: 定义了模型一次处理的序列长度（上下文窗口大小）。
-   `B`: 定义了批次大小（Batch Size），即一次迭代中包含多少个独立的训练样本。

`DataLoader` 会从长序列中随机选择一个起始点 `i`，然后：
-   **输入 (Input):** 切分出从 `i` 到 `i+m-1` 的 Token，形成长度为 `m` 的输入序列。
-   **目标 (Target):** 切分出从 `i+1` 到 `i+m` 的 Token，形成长度为 `m` 的目标序列。

**目标序列本质上是输入序列向左移动了一位。** 这样做的目的是让模型根据前面的词，预测紧随其后的下一个词。

### 示例

假设长序列为 `[x1, x2, x3, x4, x5, x6, ...]`，并且我们设置 `B=1`，`m=3`。`DataLoader` 可能生成的一个训练批次如下：

-   **输入序列:** `[x2, x3, x4]`
-   **目标序列:** `[x3, x4, x5]`

在这个样本中，模型需要学习：
-   看到 `x2` 后预测 `x3`
-   看到 `x3` 后预测 `x4`
-   看到 `x4` 后预测 `x5`

---

## 第三步：该策略的巨大优势

这种看似简单的“拼接-切片”策略非常高效，具有三大优势：

1.  **采样极其简单 (Trivial Sampling):**
    由于序列非常长，几乎可以在任何位置（从 `1` 到 `n-m`）开始切片，都能得到一个有效的训练样本。这使得数据采样逻辑变得非常简单和快速。

2.  **无需填充 (No Padding)，硬件利用率高:**
    所有生成的训练样本长度都严格等于 `m`。这完全避免了在处理变长输入时需要进行的“填充”（Padding）操作。没有了浪费计算的填充 Token，GPU 可以满负荷运行，从而极大地提高了硬件利用率，并允许使用更大的批次大小 `B`。

3.  **内存友好，支持超大规模数据集:**
    该策略天然支持流式处理（Streaming）。`DataLoader` 无需一次性将整个庞大的数据集加载到内存中。它可以按需从磁盘读取一部分数据，生成训练批次，然后在内存中释放这部分数据，再去读取下一部分。这使得训练远超单机内存容量的 TB 级数据集成为可能。

---

## 第四步：处理超大规模数据集的技巧 — 内存映射 (Memory-Mapping)

对于远超物理内存（RAM）的庞大数据集，即使是分块读取也可能变得复杂。一个更优雅且高效的解决方案是使用**内存映射 (Memory-Mapping)**。

### 什么是内存映射？

内存映射是操作系统提供的一种机制，它允许将磁盘上的文件“映射”到程序的虚拟内存地址空间。在代码中，你会得到一个行为和普通 `NumPy` 数组几乎完全一样的对象，但实际上数据的主体仍然存放在磁盘上。只有当你访问数组的特定部分（例如，通过索引或切片）时，操作系统才会“懒加载”（lazily load）那一小块数据到物理内存中。

### 如何在 NumPy 中使用？

NumPy 提供了两种便捷的方式来实现内存映射：

1.  **`np.memmap` 函数:**
    直接以内存映射模式打开一个二进制文件。
    ```python
    import numpy as np
    # 'r' 表示只读模式
    tokens = np.memmap('large_dataset.bin', dtype='uint16', mode='r')
    ```

2.  **`np.load` 函数的 `mmap_mode` 参数:**
    如果你之前是使用 `np.save` 保存的 `.npy` 文件，加载时可以指定 `mmap_mode`。
    ```python
    import numpy as np
    tokens = np.load('large_dataset.npy', mmap_mode='r')
    ```

### 关键注意事项

1.  **指定正确的 `dtype`:**
    加载时提供的 `dtype` (如 `uint16`, `int32` 等) **必须**与文件保存时使用的 `dtype` 完全一致。类型不匹配会导致数据被错误解析，得到无意义的乱码。

2.  **验证数据:**
    加载后，建议进行一个简单的验证，确保数据正确。一个有效的方法是检查数组中的最大值是否超过了你的词汇表（Vocabulary）大小。如果你的词汇表有 50,257 个词，而数组中出现了大于此数的值，那么很可能是 `dtype` 指定错误或文件本身已损坏。

通过使用内存映射，`DataLoader` 在随机访问 `tokens[i:i+m]` 时，可以无缝地、高效地只加载所需的一小部分数据，从而以极低的内存占用处理海量数据集。

## 特殊情况：如何处理分隔符？

一个常见的问题是：如果采样的窗口恰好跨越了文档边界，包含了 `<|endoftext|>` 这样的分隔符怎么办？

**答案是：分隔符被视为一个完全普通的 Token，直接放入训练数据中。**

这样做是有意为之的，它能带来一个关键的好处：**模型将学会生成分隔符**。
通过在训练中不断看到 `<|endoftext|>`，模型会学习到在什么语境下（例如，一段完整意思的文本结束后）应该生成这个 Token。这使得模型在后续的推理和生成任务中，能够自己判断何时结束一段话或一个文档，从而生成结构更清晰、更完整的文本。
